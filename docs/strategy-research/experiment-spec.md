# 키움 조건검색 기반 첫 전략 비교 명세

이 명세는 **추세 교차·최고종가·단기 되돌림 세 전략군을 같은 운용 조건에서 비교**하기 위한 구현 전 설계안이다. 사용자는 여러 전략군 비교와 키움 조건 호환을 요구했으며, 아래 숫자는 이를 구체화한 연구 기본값이다. 최적값·투자 권고·실측 성과가 아니다. 현재 데이터는 [인수 기준](backfill-contract.md)을 통과하지 않았고 HTS 일치 검증도 미실시이므로, 수익성 판단과 실거래 승인은 내리지 않는다.

## 실험 구조와 실행 전 조건

먼저 조건 대응표의 단일 항목을 Python으로 재현하고 HTS 결과와 맞춘다. 그 뒤 아래 6개 후보를 동일 조건으로 비교한다. 마지막으로 시간 분리 평가와 비용 민감도를 검토한다. 이 순서를 바꾸어 전체 기간의 최고 성과부터 고르지 않는다.

| 단계 | 산출물 | 통과 기준 |
| --- | --- | --- |
| E0 데이터 | 고정 버전 일봉·종목 이력·달력·가격 조정 설명 | 인수 문서의 연구 가능 등급 명시 |
| E1 조건 일치 | 단일 조건별 Python/HTS 종목 집합과 차이 사유 | 동일 데이터·시점에서 설명되지 않은 차이 0 |
| E2 예비 비교 | 조정가격 수익률 기반 6개 후보 결과 | 주수·실체결 검증으로 오인하지 않고 편향을 표시 |
| E3 운용 검증 | 원가격·기업행사·주수·시점별 실제 비용을 반영한 거래 장부 | 추가 데이터 게이트 통과 및 거래 표본 검산 |
| E4 시간 분리 평가 | 과거 구간별 성과와 잠금 구간 평가 | 규칙·데이터·시도 기록 고정 후 평가 |

E1은 대규모 HTS 과거 조회를 전제로 하지 않는다. 향후 동일한 마감 기준으로 확보한 HTS 검색 결과와 그 시점 데이터 스냅샷을 저장해 검증한다. 오래된 날짜를 현재 HTS로 재현했다고 주장하지 않는다. 키움 항목이나 입력 범위가 지원되지 않는 후보는 재정의 후 새 버전을 부여하며, Python 전용 조건을 몰래 추가하지 않는다.

## 신호의 정확한 계산안

`t`는 완료된 KRX 거래일, `C_t`는 조정 종가, `V_t`는 거래량이다. `SMA_n(t)`는 t 포함 n개 유효 일봉의 단순평균이다. `lag`와 롤링 창은 공식 거래일 축에 맞추며, 수집 누락을 건너뛰어 n일로 세지 않는다. 거래정지일의 봉 처리와 조정 거래량의 의미는 E1에서 키움 기준과 대조한다. 분모 0, 창 부족, 누락이 있으면 조건값은 미확정으로 두고 신규 진입에서 제외한다.

아래는 세 가지 가설에 두 값씩만 둔 **6개 후보**다. 같은 행의 대안 숫자만 변경하고 나머지 조건은 유지한다. 허용 입력 범위와 계산 경계는 [조건 대응표](condition-map.md)를 따라 확인한다.

| ID | 가설 | 매수 후보 정의 | 최초 후보 값 |
| --- | --- | --- | --- |
| T1 | 이동평균 교차 뒤 상승이 이어지는가 | `SMA_a(t-1) < SMA_20(t-1)` AND `SMA_a(t) > SMA_20(t)` | a=5, 10 |
| T2 | 종가 고점 갱신 뒤 상승이 이어지는가 | `C_t > max(C_{t-n},...,C_{t-1})` | n=20, 60 |
| T3 | 중기 상승 종목의 단기 하락이 되돌아오는가 | `C_t > SMA_60(t)` AND `100*(C_t/C_{t-3}-1) <= -d` | d=3, 5 |

T2는 **우리의 엄격한 이전 n봉 최고종가 돌파 정의**다. 키움의 `최고종가` 항목과 현재 봉 포함·등호·근접 옵션이 같다고 아직 확정하지 않았다. 이 후보는 설정 및 대조를 통과할 때만 E2에 넣는다. 지원되지 않으면 별도 정의로 바꾸고 세 전략 비교가 완료됐다고 보고하지 않는다. T3의 3봉 수익률은 t-3에서 t까지이며, 하락 후 반등 확인은 추가하지 않는다.

전략군 공통 거래량 필터의 제안은 `[일] 1봉전 거래량 >= 100,000`이다. 키움 전일거래량 조건과 대응하며 거래대금 단위 미확정 문제를 피한다. 고가·저가 종목에서 같은 거래량의 유동성이 다르므로 이것만으로 주문 가능성을 보장하지 않는다. 이 숫자도 이번 비교에서 최적화하지 않는다. 별도의 거래량 급증 효과는 1차 6개 실험에 섞지 않는다.

## 공통 계좌·매매 규칙

매수 신호의 효과를 비교하기 위해 1차 실험의 매도는 **10거래일 보유 후 다음 지정 시가 청산**으로 통일한다. 가격 기반 매도식은 후속 실험으로 분리한다. 보유기간·금액·후보 초과 처리는 조건검색 밖의 계좌 운용 규칙이다.

| 항목 | 연구 기본값 및 처리 |
| --- | --- |
| 투자대상 | 해당 날짜 코스피 보통주. 현 마스터로만 선정하면 반드시 `current-universe exploratory`로 표시하고 역사적 코스피 성과로 해석하지 않음 |
| 판단 시점 | t 마감 데이터 확정 및 적재 확인 후. 당일 데이터가 미완료이면 전일을 당일로 간주하지 않음 |
| 진입 | t+1 시가 주문 시도. 매수 미체결은 그날 취소하며 다음 신호 없이는 이월하지 않음 |
| 최대 보유 | 10종목, 종목당 진입 목표는 직전 종가 계좌 가치의 10%, 현금 부족 시 비용 포함 가능액까지 축소 |
| 중복·교체 | 기존 보유 종목 추가 매수 없음. 자리가 없으면 신규 후보를 건너뜀. 기존 보유 종목 강제 교체 없음 |
| 후보 초과 | `SHA256("v1|20260910|신호일 YYYY-MM-DD|종목코드")` 오름차순으로 배정. 해시 동률은 코드순. 미래정보를 쓰지 않는 고정 동률 규칙이며 수익 순위가 아님 |
| 청산 시점 | 거래일 u 시가 진입 시 거래일 인덱스 u+10의 시가에 청산 시도. u부터 u+10까지 10개의 일간 보유 간격 |
| 처리 순서 | 예정 매도 후 신규 매수. 같은 날 청산한 종목 재진입 금지. 판단에 당일 종가 사용 금지 |
| 방향·자금 | 매수 후 매도만, 레버리지·공매도 없음. E3 예시 초기자금 1,000만 원은 연구값 |
| 현금 | 연구 기본 현금 이자 0. 현금 비중과 평균 시장 노출을 함께 표시 |

서버는 사용자 안내상 평일 저녁 17:25 이후 가동하므로 KRX 마감 직후 수집을 당연히 가정하지 않는다. KRX 데이터의 최신 거래일을 검사해 저녁에 후보를 준비하고 다음 거래일 주문을 계획한다. 자동 주문 구현은 이 문서 범위 밖이다.

### 조정가격 연구와 실제 주수 검증

E2에서는 초기 가치를 1로 정규화하고 분할 가능한 연구 포지션을 사용한다. 조정 OHLC의 비율로 손익을 계산하되, 그 수량을 실제 주식 수로 해석하지 않는다. 일관된 가격 조정 정의는 이 단계에서도 필요하다. 수정주가에 배당이 포함되는지 모르면 결과는 총수익률로 부르지 않고, 배당과 일치하는 비교지표만 사용한다.

E3에서는 실제 원가격, 기업행사·조정계수, 주식 수와 현금 변동을 반영한다. 분할 때 주수 변경, 배당 중복 반영 방지, 합병·상장폐지의 현금 정산 규칙을 명시한다. 매수는 비용을 포함한 예산 내 정수주로 내리고, 불가능한 주문은 거절 장부에 남긴다. **현재 조정 OHLC만으로 원화 최소주문·호가단위·역사적 거래대금 제한을 검증했다고 주장하지 않는다.**

### 거래 불가·비용·결측

- 거래량 0·거래정지·OHLC 누락은 신규 매수 불가다. 당일 총거래량으로 주문량을 결정하지 않는다. E3 주문량 한도는 직전 20거래일 평균 거래량의 0.1%라는 연구 상한을 적용하고, 정지 및 가격제한 규칙을 별도로 적용한다.
- 만기 매도 불가 시 포지션과 현금을 유지하고 다음 거래일에 재시도한다. 신규 매수로 가정해 현금을 부풀리지 않는다. 상장폐지는 마지막 종가에 무조건 청산하지 않고 확인한 정산 근거를 적용한다.
- 가격이 결측인 보유 포지션은 마지막 검증 가격을 평가에만 사용할 수 있으며 경과일을 기록한다. 결측 구간에 체결시키지 않는다. 미해결 정산·평가 결측이 남으면 확정 성과 대상에서 제외한다.
- E2는 편도 거래대금의 10/30/50bp(0.10/0.30/0.50%)를 **전체 비용의 가상 민감도 시나리오**로 비교한다. 세 가지는 실제 키움 수수료·세율이라는 뜻이 아니며 서로 더하지 않는다. 기준 보고는 30bp, 10·50bp는 민감도다.
- E3는 날짜별 수수료·매도 세금·슬리피지를 별도 필드로 산정한다. 실제 값은 공식 이력과 계좌 조건 확인 전 미확정이다. 근거 없는 고정 세율을 2015년부터 적용하지 않는다.
- 일봉으로 장중 손절·익절의 선후 순서를 알 수 없으므로 1차 실험에는 장중 손절·익절을 넣지 않는다. 시가 체결도 가정이므로 한 거래일 지연한 결과를 별도 스트레스 검사로 남긴다.

## 기간 분리와 과최적화 제한

백필이 2015-01-02부터만 가능하면 최초 성과일은 최장 지표 및 전봉 계산에 필요한 61개 유효 일봉 이후로 미룬다. 가능하면 지표 준비용으로 2014년 가격을 별도 확보하되, 요청된 백필 범위를 몰래 확대하지 않는다.

| 구간 | 용도 |
| --- | --- |
| 2015~2019 | 준비 구간을 제외한 초기 개발·조건 확인 |
| 2020, 2021, 2022, 2023 각 연도 | 직전까지의 데이터로 조건을 고정하고 다음 1년 평가 |
| 2024-01-01~2026-09-09 | 이번 설계에서 제안하는 최종 잠금 구간. 아직 전략 성과를 조회하지 않음 |

6개 후보를 모두 같은 연도에 평가하고 성과가 좋았던 후보만 보고하지 않는다. 한 전략 선택이 필요하면 각 평가 연도 직전까지의 데이터에서 비용 차감 연간 수익률 중앙값으로 선택하고, 동률이면 최대낙폭이 작은 후보, 다시 같으면 ID·파라미터 숫자 오름차순으로 정한다. 이는 사전 선택 규칙이며 모든 후보의 결과도 함께 보존한다.

각 분리 평가의 거래는 첫 평가일 이후 진입하고 신규 계좌에서 시작한다. 학습 결과를 계산할 때 만기·가격 정보가 학습 종료일을 넘는 거래는 학습 거래 통계에서 제외한다. 평가 말일 미청산 포지션은 보유 평가손익을 포함하고 별도 표시한다. 이 구간별 초기화 결과를 하나의 실제 연속 계좌라고 이어 붙이지 않는다. 연속 운용 평가는 별도 실행 ID로 남긴다.

잠금 구간을 열어본 후 규칙을 바꾸면 그 구간은 개발 구간으로 재분류한다. 이미 사용자가 해당 구간에서 전략을 반복 선택한 이력이 있다면 완전한 미사용 검증으로 주장하지 않는다. 더 긴 미사용 데이터나 이후 전진 기록이 필요하다. 6개 후보×3개 비용은 18개 결과이며, 비용 시나리오를 별개의 알파 발견으로 세지 않는다. 체결 지연 검사는 기준 비용의 6개 후보에만 추가해 총 24개 실행으로 시작한다.

## 평가표와 후보 유지 기준

시장 비교는 종합(KOSPI)의 동일 기간 가격 수익률, 통제 비교는 같은 역사적 투자대상·거래비용 가정의 월간 동일비중 포트폴리오를 제안한다. 지수는 직접 매매 상품이 아니므로 거래 가능한 ETF와 동의어로 취급하지 않는다. 배당 기준·시장 노출·재조정 시점이 다르면 차이를 표시한다.

결과에는 연복리수익률, 일별 변동성, 최대낙폭, 최장 회복기간, 연도별 성과, 현금 비중, 회전율, 거래 건수, 비용 총액, 종목별 손익 기여도와 미체결 사유를 포함한다. 연환산 기준은 거래일 252일, CAGR은 실제 경과일/365.25로 고정하고 사용 라이브러리의 기본값에 맡기지 않는다. 회복하지 못한 낙폭은 관측 종료일까지의 하한 기간과 미회복 상태를 표시한다.

후속 검토 후보는 시간 분리 평가 합산 비용 차감 수익이 양수이고, 4개 평가 연도 중 최소 3개가 양수이며, 비용 50bp와 하루 지연 각각에서 합산 수익이 양수인 경우로 제안한다. 이 기준은 수익 보장이나 통계적 유의성 판정이 아니다. 탈락해도 연구 결과로 보존한다. 거래 100건 미만 또는 특정 한 종목이 총 양의 손익 기여의 25%를 넘으면 근거 부족/집중 표시를 추가한다. 사용자의 허용 최대낙폭이 미정이므로 실운용 적합 판정은 보류한다.

## 구현자에게 넘길 결과 형식

각 실행에는 `run_id`, 코드 커밋과 작업트리 변경 해시, 데이터 manifest 해시, 전략 ID·조건 버전, 기간·대상·비용·난수 시드, 엔진 종류·버전, 거절 규칙을 기록한다. HTS 조건명과 설정은 별도 정의 파일로 관리하고 임의 파라미터 탐색을 자동 추가하지 않는다.

필수 결과는 신호 일자별 후보 종목, 주문·체결·거절 장부, 일별 현금·포지션·총자산, 구간별 성과, Python/HTS 차이 목록이다. 원본 데이터를 대화에 덤프하지 않고 집계와 작은 오류 표본으로 검토한다. 코드 구현은 이 명세 이후의 작업이며 이번 작업에서 백테스트를 실행한 것은 아니다.

기술적 연결점은 현재 저장소 `vectorbt/portfolio/base.py`의 `from_signals`, `from_orders`, 자금 공유·주문 순서 설정과 `vectorbt/generic/splitters.py`다. 동일 종목당 독립 계좌 결과를 합해 실제 공동 계좌라고 보고하지 않는다. 특수 체결·기업행사 처리에 추가 구현이 필요한지는 E3에서 확인한다.
