# 데이터 인수 조사와 병렬 작업 순서

이 문서는 실제 백테스트 실행 전에 무엇을 병렬로 조사하고 어떤 조건을 순서대로 통과해야 하는지 정리한다. **원천 조사·가격 패턴 분석·데이터 계약 대조는 병렬로 진행할 수 있다. 실제 수익률 실행은 데이터 인수와 시장 모형 구현 검증 이후다.** 2026-09-13 조사 범위는 2015~2023년 가격과 수집 코드·스키마이며, 2024-01-01~2026-09-10 잠금 가격은 사용하지 않았다. 현재 판정은 `BLOCKED` / `NO_SELECTION`을 유지한다.

먼저 병렬 작업표에서 역할과 의존성을 확인하고, 관측 결과에서 데이터 문제의 범위를 읽는다. 보완 목록은 공급 자료와 프로그램 구현을 구분하며, 마지막의 증거와 검증은 판단을 재확인하는 데 사용한다.

## 1. 조사 세 갈래를 합친 뒤 인수와 실제 실행을 진행한다

사용자는 이번 작업에서 에이전트와 적절한 모델을 선택한 병렬 작업을 승인했다. 다음은 작업 배분이며 모델 성능이나 비용의 실측 비교는 아니다.

| 작업 | 배정 모델 | 독립 수행 범위 | 합류 조건 |
| --- | --- | --- | --- |
| ① 원천·수집 코드 조사 | gpt-5.6-sol | 수집·변환·조정 플래그·실행 이력 대조 | 관측된 가격 패턴과 원천 표본 연결 |
| ② 비정상 OHLCV 분석 | gpt-5.6-sol | 고정 스냅샷의 오류 유형·공급자·연도·종목 집계 | 원인 확정에는 ①의 증거 필요 |
| ③ 데이터 계약 대조 | gpt-5.6-luna | 실제 테이블과 필수 입력·구현 누락 대조 | ①② 결과를 반영해 보완 목록 확정 |
| 통합·서버 확인·실행 경계 검증 | 주 에이전트 | 읽기 전용 DB 집계, 교차 검산, 최종 판정 | 데이터와 소프트웨어 완료 조건을 함께 확인 |

흐름은 **① ∥ ② ∥ ③ 초안 → 원인·보완 목록 통합 → 자료 보완과 계약에 따른 합성 검증 → 데이터 인수·실행 모형 검증 통과 → ④ 2015~2023 실제 전략 비교 → 후보·정책 고정 → 잠금 평가**다. 공급 자료를 기다리는 동안에도 확정된 상태 계약에 대한 합성 테스트와 어댑터 구현은 병렬로 진행할 수 있다. 추정한 가격 의미를 구현에 고정하거나 실제 수익률로 확인해서는 안 된다.

## 2. 서버 재조회에서 기존 품질 문제의 규모가 유지됐다

2026-09-13 19:28 KST에 PostgreSQL 읽기 전용 트랜잭션으로 재조회했다. 아래 값은 2015-01-02~2023-12-31 요청 범위이며 실제 마지막 봉은 2023-12-28이다. 기존 스냅샷과 집계는 같지만, 행별 해시 동일성을 검증한 것은 아니다.

| 공급자 라벨 | 행 | 종목 ID | 비정상 OHLCV | 종가 0 |
| --- | ---: | ---: | ---: | ---: |
| KIWOOM | 5,564,973 | 3,499 | 1,201 | 1,201 |
| KRX | 544,241 | 526 | 70,871 | 0 |
| 합계 | 6,109,214 | 4,025 | 72,072 | 1,201 |

전부 `adjusted=true`이며 `ka10081` 원천 응답 보관은 여전히 0건이다. 공급자 라벨과 조정 플래그만으로 조정 방식의 동일성을 확정할 수 없다. KRX 비정상 행을 KIWOOM 종가 0 문제와 같은 원인으로 취급하지 않는다.

홈서버의 6개 컨테이너는 조회 당시 모두 healthy였다. 수집 저장소의 로컬 HEAD는 `63c1e2753267260724779aa045e5ca3696e3c911`, 서버 HEAD는 `69747e6cc658ac3cda4f20ffd4410feb0c930a87`이다. 현재 코드와 과거 각 배치의 실제 실행 코드는 별도로 증명해야 한다.

## 3. 두 가격 문제는 저장 경로가 다르며 원천 대조가 남았다

고정 스냅샷의 62개 Parquet 파일 해시를 확인하고 최대 10만 행씩 재집계했다. 비정상 행·거래량 0·공급자·연도별 합계의 내부 검산은 통과했다. 자세한 종목·연도 분해는 [품질 집계 JSON](quality/quality-audit.json)과 [재현 스크립트](quality/audit_snapshot_quality.py)에 있다.

아래 세부 유형은 중복 없는 분할이다. 거래량 0 자체를 오류로 판정한 것이 아니라, 이미 OHLCV 규칙을 위반한 행을 거래량으로 나눴다.

| 관측 유형 | 행 | 확인한 사실 | 아직 확정하지 못한 원인 |
| --- | ---: | --- | --- |
| KIWOOM 종가 0·거래량 양수 | 695 | `102950`의 종가 0 | 공급자 수정주가 정밀도, 과거 응답 값·변환 |
| KIWOOM 종가 0·거래량 0 | 506 | 위 종목의 나머지 종가 0 | 당시 거래 상태와 원천 표기 |
| KRX 고가 < 종가·거래량 양수 | 7,935 | 거래량이 있어 단순 무거래 표기로 일괄 설명 불가 | 원 DataFrame의 조정·스케일·필드 의미 |
| KRX 고가 < 종가·거래량 0 | 62,936 | 이 중 62,647행은 시가·고가·저가가 모두 0, 종가는 양수 | 거래정지·정상 비거래·결측 변환을 원천으로 구분해야 함 |
| 합계 | 72,072 | 기존 품질 판정과 동일 | 인수 차단 유지 |

**코드에서 확인한 사실:** 키움 경로는 수정주가 모드를 요청하고 응답 정수 문자열을 `int`로 변환한다. 양의 정수 문자열을 반올림해 0으로 만드는 로직은 확인되지 않았다. 소수 문자열은 현재 파서에서 `None`이 된다. 다만 실제 과거 원문이 없어 `102950`의 원인을 확정하지 못했다. KRX 경로는 `pykrx adjusted=True` 결과를 `int(value)`로 변환하고 변환 실패·NaN은 0으로 만든다. 매퍼는 종가가 0 이하인 행만 건너뛰며 고가·종가 관계를 검사하지 않는다. 따라서 이상 행이 저장될 수 있는 경로는 확인했지만, 원천부터 이상했는지까지 확인한 것은 아니다.

**계보의 한계:** `data_vendor`는 마이그레이션 022에서 기존 행에 기본값 `KIWOOM`을 부여했다. 과거 코드 비교와 실행 기록은 있으나 원 응답·불변 실행 manifest가 없어 행별 원천을 재현하지 못한다. 현재 `raw_response` 모델만으로 원문 저장이 보장되지 않는다. 공급자별 조정 정의, 배당 포함 여부, 가격·거래량 단위, 반올림과 소급수정 정책을 별도로 받아야 한다.

## 4. 추가 납품 자료와 여기서 할 구현을 구분한다

테이블 존재와 인수 가능 여부는 다르다. 다음 표는 이번 조사에서 확인한 테이블 후보와 보완 계약이다. signal DB의 보조 테이블은 인접 저장소 모델·명세 기준이며 이번 세션에 해당 DB 내용을 재집계하지 않았다. 자료 제공자에게 메시지를 보내거나 수집을 실행한 것은 아니다.

| 입력 | 기존 테이블·후보 | 공급 자료에서 보완할 것 | 이 저장소에서 할 일·완료 조건 |
| --- | --- | --- | --- |
| 원가격·조정가격 | `kiwoom.stock_price_krx`, 검증용 `kiwoom.raw_response` | 수정/비수정 원문, 단위·계수·반올림·버전. `102950` 0 전후와 KRX 양수 거래량의 고가<종가 표본 우선 | 가격 종류별 스냅샷과 계보 해시. 원문→DB 재현, 미해결 오류는 인수 차단 |
| 기업행사·조정 계보 | signal DB `public.corporate_event`, `public.dart_disclosure`, `public.dart_corp_mapping` | 해당 테이블의 역사 완전성, 가격/수량 계수, 효력일·원문·코드 승계·상폐 정산 | 분할·병합·배당·잔여주·현금 정산 어댑터와 독립 장부 대조 |

| 거래정지·재개·상폐 | `kiwoom.stock.state/is_active/delisted_date`는 현재값 | 사건별 시작·종료·사유·정산 원장. 현재 `delisted_date` 주석은 마지막 수집 거래일이므로 독립 상폐일 증거 필요 | 비거래와 결측 분리, 정지 체결 금지, 만기 재시도·상폐 보유분 정산 |
| 공식 거래일 | 전용 테이블 미확인 | 시장별 개장·휴장·단축장과 출처 | 기대 행·누락 판정, 달력 1개월 만기 계산. 지수 관측일을 공식 달력으로 간주하지 않음 |
| 현실 비용·호가 | 전용 역사 비용 테이블 미확인 | 날짜·시장·매수/매도별 요율, 계좌 조건, 호가·가격제한 이력, 슬리피지 근거 | 날짜별 비용·호가 어댑터. 10/30/50bp 민감도 가정과 실측/공식 기준 구분 |
| 실행·정정 기록 | 로컬 snapshot manifest는 일부 구현 | 실행 commit/image digest/인자/요청 모드, 페이지별 건수, 원 로그, 변경 전후 해시·사유 | 모든 입력 파일을 고정하고 수정은 새 revision·새 실험으로 보존 |

**우선 보완 묶음:** (1) `102950` 수정/비수정 응답과 기업행사, (2) KRX 고가<종가의 거래량 양수·0 각각의 원 DataFrame/dtype와 수정/비수정 비교, (3) 그 값을 만든 실행 버전·명령·단위·조정 정의다. 재조회 값은 과거 수집 원문을 대체하지 않으므로 취득 시각과 소급수정 가능성도 남긴다. 이 표본으로 공급자 변환 문제인지 상태 모형 문제인지 나눈 뒤 전체 보완 범위를 확정한다.

## 5. 실제 실행에는 데이터와 프로그램 두 조건이 필요하다

현재 추출 코드는 `kiwoom.stock_price_krx`와 `kiwoom.stock`을 읽는다. `kiwoom.raw_response`는 원천 확인용이다. 인접 `ted-startup`의 signal DB 가격 이관 완료나 해당 프로젝트 검증 PASS는 이 연구 프로그램의 데이터 인수 PASS를 뜻하지 않는다.

현재 `quality.py`는 실제 자료를 최대 `EXPLORATORY_ADJUSTED`까지만 판정하며 `EXECUTION_ELIGIBLE` 인수를 구현하지 않았다. `runner.py`는 비합성 자료를 `ADJUSTED_SHARE_MODEL_NOT_VALIDATED`로 차단한다. `freeze/finalize` 및 후속 배치 단계도 미완료다. 따라서 manifest 플래그 변경이나 비정상 행 제외만으로 ④를 실행할 수 없다.
